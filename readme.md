# Support & Operations ReAct Agent

An AI-powered internal **Support & Operations Assistant** built with **LangGraph, LangChain, Gemini, Tavily, RAG, SQLite, and Human-in-the-Loop workflows**.

The agent can retrieve internal company policies, search the public web when appropriate, ask humans for clarification when information is missing, and perform approved database updates safely.

---

## 🚀 Overview

The Support & Operations Agent is designed around a **ReAct (Reasoning + Acting)** workflow.

Instead of answering every request directly, the agent decides which tool should handle the request:

```text
                         ┌──────────────────────┐
                         │      User Query      │
                         └──────────┬───────────┘
                                    │
                                    ▼
                         ┌──────────────────────┐
                         │   ReAct AI Agent     │
                         │      (Gemini)        │
                         └──────────┬───────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
              ▼                     ▼                     ▼
        ┌───────────┐        ┌────────────┐        ┌─────────────┐
        │    RAG    │        │ Web Search │        │ Ask Human   │
        │ Internal  │        │  Tavily    │        │ Clarify /   │
        │ Knowledge │        │            │        │ Escalate    │
        └───────────┘        └────────────┘        └─────────────┘

                           ┌─────────────────┐
                           │ SQLite Database │

                           └─────────────────┘
```

# ✨ Features

### 1. Internal Knowledge Base RAG

The agent uses a local knowledge base for internal information such as:

* Ticket management policies
* Ticket statuses
* Refund policies
* Security policies
* Escalation procedures

The current implementation uses **TF-IDF + cosine similarity** to retrieve relevant sections.


The agent retrieves the internal ticket closure policy instead of relying on general model knowledge.

---

### 2. Public Web Search

For information that requires current public knowledge, the agent can use **Tavily Web Search**.



The agent routes this request to the web-search tool instead of treating it as an internal policy question.

---

### 3. Human-in-the-Loop

The agent does not guess when critical information is missing.

For ambiguous requests such as:



The workflow then resumes using the human's response.


---

### 4. Safe Database Operations

The agent can update support ticket records stored in SQLite.



Database changes require human approval before execution.

The database tool also uses an `operation_id` to prevent the same operation from being executed twice.

This provides a basic **idempotency mechanism** for operational writes.

---

### 5. Security Rules

The agent is instructed not to expose:

* Passwords
* API keys
* Access tokens
* Credentials
* Other sensitive secrets

Security-related incidents are routed according to the internal security policy.

---

### 6. Evaluation Framework

The project includes separate evaluation components for:

* Tool-selection accuracy
* RAG grounding
* End-to-end routing
* Trace analysis

The evaluation framework is designed to measure actual agent behavior rather than relying only on example conversations.

Actual evaluation percentages should be generated by running the evaluation scripts.

## 1. Clone the repository

```bash

cd support_ops_agent
```

## 2. Create a virtual environment

```bash
python -m venv .venv
```

Activate it on Windows:

```bash
.venv\Scripts\activate
```


# 🧪 Evaluation

The project contains three main evaluation scripts.

## Tool Routing Evaluation

Tests whether the agent selects the appropriate tool.

```bash
python -m evaluation.evaluate_routing
```

The evaluation covers:

* RAG routing
* Web-search routing
* Human clarification
* Database-write routing

---

## RAG Grounding Evaluation

Tests whether answers contain the important facts expected from the internal knowledge base.

```bash

```

The test cases cover:

* Ticket closure
* Ticket statuses
* Refund eligibility
* Refund approval
* Security incidents

The test set includes:

* Public information requests
* Ambiguous requests
* Database operations
* Security scenarios

# 🔐 Safety Design

The agent follows several safety principles.

### Internal vs External Knowledge

Internal company policies should be retrieved from the internal knowledge base rather than replaced with public web information.

### No Guessing

When required information is missing or ambiguous, the agent can request human clarification.

### Human Approval

Database-changing operations require explicit human approval.

### Idempotency

Database operations use an `operation_id` to avoid executing the same operation twice.

### Secret Protection

The agent is instructed not to expose credentials, API keys, passwords, or tokens.

# 🎯 Design Goals

This project focuses on building an agent that is:

* **Grounded** — internal policy answers come from the knowledge base.
* **Tool-aware** — different information needs use different tools.
* **Safe** — critical actions require human approval.
* **Non-guessing** — ambiguity can trigger human clarification.
* **Traceable** — tool usage and outputs are logged.
* **Evaluatable** — behavior can be measured using predefined test cases.
* **Idempotent** — repeated database operations can be detected.

# 🚧 Current Limitations

The current version is intentionally a practical prototype.

### Retrieval

The RAG implementation currently uses TF-IDF rather than a production vector database or embedding model.

### Database

SQLite is used for simplicity and local development.

### Evaluation

The evaluation suite currently focuses heavily on tool routing and grounding. More sophisticated semantic evaluation can be added later.

### LLM Dependency

Agent decisions depend on the configured Gemini model and its available API quota.
